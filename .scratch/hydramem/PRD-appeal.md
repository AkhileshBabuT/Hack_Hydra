# PRD — The appeal path: recovering false abstentions

> *This was generated by AI during triage.*

Status: ready-for-agent
Source: `hydramem-verification-cascade.md` + grill session 2026-08-16
Parent: `.scratch/hydramem/PRD.md` — this is a second PRD under the same track,
not a replacement.

## Problem Statement

HydraMem abstains on **86 of 150 questions**, and **60 of those 86 are wrong** —
questions the graph could have answered, thrown away. That single fact is the
entire accuracy gap: 0.4933 against vector RAG's 0.6467.

It is worse than "answers less often." `answerable_accuracy` is **0.4000**
against full_context's 0.5750 and vector_rag's 0.5833, so on the questions it
does choose to answer it is also the least accurate arm. The comfortable framing
— *answers less often, more trustworthy when it does* — is not supported by the
generated data and must not be written anywhere.

The 60 false abstentions are not one failure. They are three, and they need
different fixes:

| reason | n | when it fires |
|---|---|---|
| `not_in_graph` | **27** | after the model, holding the facts, declined |
| `no_such_relation` | 16 | gate 2, before retrieval |
| `unknown_entity` | 15 | gate 1, before retrieval |
| `no_fact_in_window` | 2 | gate 3, before retrieval |
| `no_path` | **0** | gate 4 never fires at all |
| `fabricated_citation`, `uncited_answer` | **0** | gate 5 strictness costs nothing |

**This PRD addresses only the 27.** They are the largest single bucket, and they
share a root cause with the worst category in the harness
(`single-session-assistant`, 2 of 20 against 20/20 and 18/20) — a cause CLAUDE.md
currently records as *not located*.

The user-facing shape of the problem: a person asks their memory a question, the
answer is sitting in their own history, and the memory says it does not know.

## Solution

An **appeal**. When the cascade abstains, the question gets one second look —
with evidence the first call did not have — and the appeal may only ever overturn
*toward answering*. It can never turn an answer into an abstention.

Three properties make this safe rather than a confidence hack:

1. **It is not a gate, and no model runs inside one.** The gates decide first and
   keep deciding lexically. The appeal runs after an abstention has already been
   returned, so the first non-negotiable in CLAUDE.md is untouched.
2. **It only moves in the direction the codebase already sanctions.** CLAUDE.md
   fixes the bias: *an unrecognised question passes; a false pass costs one model
   call and still meets the citation check.* An appeal that can only convert
   ABSTAIN → ANSWER moves the same way. Gate 5 still audits whatever it produces,
   unchanged and unrelaxed.
3. **The new evidence is real, not a re-roll.** `llm.py` caches on the request, so
   re-asking the identical question with the identical facts returns the identical
   refusal forever. The appeal must therefore change the evidence, not the
   temperature.

The evidence it changes is the **verbatim span width**. Every Fact already carries
a `snippet` — the extractor's chosen evidence span, capped at 240 characters — and
that snippet already reaches the answering model inside each fact line. The appeal
re-renders the same facts at a **wider span** and asks again. Nothing leaves the
graph, no new node label is introduced, and no new Cypher is written.

This is the verification-cascade document's §2(a) fix — Zep's −17.7pp loss on
`single-session-assistant`, caused by extraction discarding exactly what that
category asks about — but placed as an appeal rather than as a router flag, which
makes it cheap, ablatable, and reachable by questions outside the two categories a
router would have tagged.

## User Stories

1. As someone asking my memory a question, I want it to try twice before telling
   me it does not know, so that a fact sitting in my own history is not lost to a
   truncated quote.
2. As someone asking my memory a question, I want the second attempt to see more
   of what I actually said, so that the retry is a real second look and not the
   same question asked louder.
3. As someone asking my memory a question, I want an answer that survived the
   appeal to be audited exactly as strictly as one that did not, so that the
   second chance does not buy a weaker guarantee.
4. As someone asking my memory a question, I want the appeal never to take away an
   answer I already had, so that enabling it cannot make the system worse for me.
5. As someone reading `explain()`, I want the trace to say an appeal happened, what
   triggered it, and whether it changed the outcome, so that an answer's history is
   visible rather than inferred.
6. As someone reading `explain()`, I want an appeal that failed to be as legible as
   one that succeeded, so that "we tried and the answer really is not there" is a
   reportable result.
7. As a judge reading the results table, I want the abstention count broken down by
   reason, so that "it abstains a lot" becomes "it abstains for these four
   distinguishable causes in these proportions."
8. As a judge reading the results table, I want the false-abstention count reported
   beside the true one, so that abstention recall cannot be read as a virtue on its
   own.
9. As a maintainer, I want the per-reason breakdown generated into `docs/eval/`
   rather than computed by hand, so that every number in it is regenerable and
   falsifiable.
10. As a maintainer, I want the appeal switchable off, so that its contribution is
    an ablation rather than a claim.
11. As a maintainer, I want the appeal's effect reported as a delta on the
    `not_in_graph` count specifically, so that it cannot be confused with a general
    accuracy drift.
12. As a maintainer, I want the appeal decision reproducible from a reason string
    and a list of dicts, so that I can debug an appeal without a database or a
    model.
13. As a maintainer, I want the appeal's round-trip cost pinned by the fixture
    suite, so that "at most four Bolt round trips" stays a counted claim.
14. As a maintainer, I want the appeal to add **zero** Bolt round trips, so that the
    cost story changes only in tokens, in one direction, on one bucket of questions.
15. As a maintainer, I want the render width to default to today's behaviour, so
    that introducing the parameter changes no existing output.
16. As a maintainer, I want the wider storage cap isolated in its own issue, so that
    the work needing a wipe is separable from the work that does not.
17. As a maintainer, I want to know how many appeals fired and how many succeeded,
    so that an appeal path that never fires is distinguishable from one that is
    broken — the failure mode CLAUDE.md records for every gate so far.
18. As a maintainer, I want the appeal to leave gate 5 untouched, so that the
    citation guarantee is not quietly renegotiated to make the appeal look better.
19. As a maintainer, I want an appeal that produces a fabricated citation to be
    discarded loudly, so that a second chance cannot launder an ungrounded answer.
20. As a maintainer, I want to know the token cost of appeals separately from the
    base cost, so that the 6.2x claim can be restated honestly rather than defended.
21. As an agent author using the mem0 surface, I want `search()` to benefit from the
    appeal without any API change, so that the improvement is not something I have
    to opt into.
22. As an agent author, I want `explain()` to keep working unchanged, so that the
    appeal does not fork the debugging path from the demo path.

## Implementation Decisions

**The appeal decision is a pure function; the orchestration is a thin wrapper.**
The decision takes the abstention reason and the facts already in hand, and
returns an appeal plan — whether to appeal, over which facts, at what render
width. It touches no driver and no model, so it is tested over plain dicts. This
follows the existing rule that gate predicates, chain derivation and temporal
filters are all pure; an appeal that could only be tested through a live node
would be the first decision in the cascade that is not.

**Only `not_in_graph` is appealable in this PRD.** The other three reasons fire
before retrieval, so at appeal time there are no facts in hand to re-render — a
different fix, deliberately left to a later slice. The appeal plan returns "no
appeal" for them, and that is asserted rather than assumed, so extending the set
later is a one-line change with a test that already exists.

**Span width is tiered: storage and render are separate concerns.** The extractor's
cap governs how much verbatim text the graph *holds*; the render width governs how
much of it the model *sees* on a given call. The first call renders at today's
width, the appeal renders wider. This is what makes the appeal a genuinely
different request rather than a cache hit, and it keeps the base token cost of the
questions that answer first time exactly where it is.

**Widening the storage cap is a separate issue because it is a migration.**
Snippets are written at ingest and fact ids are content-derived, so a wider cap
means a wipe, a full re-ingest and a full re-score. Every other issue here lands
without a live node. Bundling them would make the whole PRD blocked on Docker.

**No new Cypher, no new node label, no new edge type.** The appeal re-renders facts
the cascade already read. `statements.py` and its `INVENTORY` are untouched, the
6-edge-type budget is untouched, and `test_statements.py` has nothing new to probe.

**The appeal adds zero Bolt round trips and exactly one model call**, and only on
questions that already abstained. The round-trip distribution — 7 questions at 2,
141 at 3, 2 at 4, never five — is unchanged, and the fixture suite asserts that
rather than trusting it.

**Gate 5 runs on the appeal's output unchanged.** Same citation check, same
strictness, same reason codes. An appeal answer that cites a fabricated id is
discarded exactly as a first-call answer would be. The appeal cannot relax the
guarantee it is trying to get past.

**The appeal is off by default in the evaluation harness and switched on by an
explicit flag**, so the ablation is a real comparison of two runs rather than a
before-and-after across a code change. This is the direct lesson of slice 17,
which bundled three changes into one wipe-and-rescore and could not attribute the
result.

**Per-reason abstention counts become generated columns**, not a derived table.
CLAUDE.md forbids quoting a number that is not in `docs/eval/`; `not_in_graph: 27`
was computed ad hoc during the grill session and is therefore not yet quotable.
The instrumentation lands before anything claims a delta against it.

**The trace gains an appeal line.** `explain()` stays pure and stays the same code
the demo path and the debugging path both use. An appeal that fired and failed
traces as distinctly as one that fired and won — the audit record is of what was
*spent*, not only of what was decided, which is why gate 4 already traces as
`skipped` rather than `pass`.

## Testing Decisions

**A good test here holds the real payload, not a description of it.** The existing
convention is explicit: slice 06's collapsed decodes are pinned as the literal
strings the model emitted, because a paraphrase would not notice a decoder that
stopped collapsing the same way. An appeal test that asserts "the answer improved"
proves nothing; one that asserts a specific truncated snippet produced
`not_in_graph` and the widened one did not, proves the mechanism.

**Prior art, and the seams to reuse:**

- `tests/test_answer.py` — **pure**, no driver, no model. This is where the appeal
  decision, the render width and the trace text belong. It is pure by deliberate
  design: a test of the citation downgrade that depends on what a model happens to
  return proves nothing about the guarantee, and the same reasoning applies to an
  appeal decision. This file currently passes with Docker down and must continue to.
- `tests/test_fixtures.py` — **live graph, stubbed model**, 25 cases in ~10s, with
  `Case.trips` asserting the round-trip count on every one. This is where the
  appeal's zero-round-trip property is pinned, and where an appeal is exercised
  end to end against real writes and real reads.
- `tests/test_eval.py` — **pure**, over plain row dicts. This is where the
  per-reason counts are tested, alongside the existing rate maths.
- `tests/test_statements.py` — **untouched**. No new statement is introduced. If a
  change to this file becomes necessary, the design has drifted.

**What gets tested:**

- The appeal plan says *appeal* for `not_in_graph` and *do not appeal* for
  `unknown_entity`, `no_such_relation` and `no_fact_in_window` — asserted per
  reason, so widening the set later is a visible change.
- The appeal plan says *do not appeal* when there are no facts in hand, because
  re-rendering nothing wider is still nothing.
- Rendering at the default width produces byte-identical output to today, so the
  parameter's introduction is provably inert.
- Rendering wider produces strictly more verbatim text for a fact whose snippet was
  truncated, and identical text for one that was not.
- An appeal answer carrying a fabricated citation is discarded, with
  `fabricated_citation` and the invented id named — the appeal does not get a
  softer gate 5.
- An appeal never converts an answered question into an abstention. Asserted
  directly, because it is the property that makes the feature safe to enable.
- The round-trip count is unchanged by an appeal, on a real graph.
- The per-reason counts sum to the total abstention count, so the breakdown cannot
  silently drop a category.
- A question that abstained for a reason with no appeal path still returns its
  original reason code unchanged, so the appeal is not observable where it does not
  run.

**What is deliberately not tested:** whether the appeal *improves accuracy*. That
is a measurement, not a test, and it belongs in `docs/eval/` where it can be
regenerated and disagreed with. A test asserting an accuracy number would pin a
result rather than a behaviour and would go red for reasons that are not defects.

## Out of Scope

- **The 31 pre-model false abstentions** from gates 1 and 2. Real, larger in
  aggregate than they look, and a different fix — the appeal has no facts in hand
  when those fire. A later slice, and CLAUDE.md's warning applies to it: a fixture
  exercising a recogniser is written by whoever wrote the recogniser and tests the
  same blind spot twice, so those need probing against real ingested instances.
- **LongMemEval-V2 and BEAM.** Declined with reasons and reversal conditions in
  `.scratch/hydramem/.out-of-scope/longmemeval-v2-and-beam.md`.
- **The sufficiency autorater as a gate.** The verification-cascade document
  replaces gate 4 with it. Gate 4 fires **zero** times on this corpus, so the swap
  trades a vacuous gate for a per-question model call, and a rater placed before
  synthesis can only convert passes into abstentions — the wrong direction for the
  one check this system loses.
- **Learn-Then-Test conformal calibration.** The source document itself scopes it
  at 4–6 hours and warns that a subtle error yields a guarantee that is *wrong*
  rather than absent. There is no calibration slice held out for it, and the appeal
  has no threshold to calibrate — it fires on a reason code, not a score.
- **Semantic entropy / self-consistency sampling.** 5–10× inference cost, and the
  probe variant needs hidden states that NIM does not expose.
- **Risk-coverage curves and AURC.** The honest headline for an abstention system
  and nearly free to plot from cached scores — but with `answerable_accuracy` at
  0.4000 it would show HydraMem below both baselines at every coverage level. Worth
  doing *after* the appeal has moved the number, not before.
- **Adding `owns` to the counted predicates.** Strictly safe, already recorded on
  issue 17, still needs its own wipe-and-rescore. Not bundled here — bundling is
  what cost slice 17 its attribution.

failure "has not been located" — a negative appeal result locates it.
