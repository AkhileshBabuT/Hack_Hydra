# 22 — The appeal path: one second look, toward answering only

> *This was generated by AI during triage.*

Status: done — closed 2026-08-17; critic FAILed it once, all four findings fixed

## Parent

`.scratch/hydramem/PRD-appeal.md`

## Why this exists

HydraMem abstains on 86 of 150 questions and 60 are false abstentions. The
largest single bucket is `not_in_graph` — **the answering model, holding the
facts, declined**. Those 27 questions were not lost to a gate. They were lost
after retrieval succeeded, which means the facts reached the model in a form it
could not answer from.

Every Fact already carries a `snippet`, the extractor's chosen evidence span,
capped at 240 characters, and that snippet already reaches the model inside each
fact line. So the evidence is present and truncated, not absent. That is a
recoverable failure and this issue is the recovery.

## What to build

When the cascade abstains, the question gets one second look with evidence the
first call did not have, and the second look **may only ever overturn toward
answering**.

Three properties are the whole design and none is optional:

**It is not a gate.** It runs after an abstention has been returned. The gates
stay lexical and stay first, so "no model runs inside a gate" is untouched.

**It only moves one way.** An appeal can turn ABSTAIN into ANSWER and can never
turn ANSWER into ABSTAIN. This is the same bias the codebase already fixes — an
unrecognised question passes, because a false pass costs one model call and still
meets the citation check. Enabling the appeal must be incapable of making any
question worse.

**The evidence genuinely differs.** Model calls are cached on the request, so
re-asking with the same facts returns the same refusal forever. The appeal
re-renders the *same facts* at a **wider span width**. Storage width and render
width become separate concerns: the first call renders at today's width, the
appeal renders wider. The questions that answer first time keep their current
token cost exactly.

Split the work at the seam agreed in the grill session:

- **The decision is pure.** A function takes the abstention reason and the facts
  in hand, and returns an appeal plan — appeal or not, over which facts, at what
  width. No driver, no model. An appeal decision must be reproducible from a
  reason string and a list of dicts, the same property gate predicates already
  have.
- **The orchestration is thin.** Re-render, one model call, then gate 5 exactly as
  it runs today.

**Only `not_in_graph` is appealable.** The other reasons fire before retrieval,
so there are no facts in hand to re-render. The plan returns "no appeal" for them
and that is asserted per reason, so widening the set later is a visible one-line
change against a test that already exists.

**Gate 5 is unchanged.** Same check, same strictness, same reason codes. An
appeal answer citing a fabricated id is discarded exactly as a first-call answer
would be. The appeal must not be able to relax the guarantee it is trying to get
past.

**The trace records it.** `explain()` stays pure and stays the code both the demo
path and the debugging path use. An appeal that fired and failed must trace as
distinctly as one that fired and won — the trace is an audit of what was *spent*,
which is why gate 4 already traces as `skipped` rather than `pass`.

**It is switchable off**, so its contribution is an ablation between two runs
rather than a before-and-after across a code change. Default off in the harness.

## Result

Built, failed by the critic, fixed. The critic pass was worth more than the
build: it found a safety hole that would have killed an evaluation arm.

### What shipped

`plan_appeal(reason, facts, windowed)` is pure — no driver, no model — and
returns an appeal plan or a named refusal. The orchestration is a thin `ask()`
closure inside `answer_question`, reused by both calls, so gate 5 runs on the
retry unchanged. **Zero added Bolt round trips**: every fact the appeal shows
was already read for the first call. Off by default.

### The safety claim was false, and the critic caught it

The stated guarantee was "enabling the appeal can never make a question worse."
It could. `llm.complete_json` raises on exhausted retries, on a non-retryable
4xx, and on the ~5% greedy-decode collapse, and **nothing caught it** — not
`answer_question`, not `eval.run_hydramem`, not the mem0 surface. So `appeal=True`
could turn a clean abstention into an unhandled exception and no `Result` at
all, propagating into the arm loop. This project has already lost a 150-question
arm to that exact failure class.

Now caught broadly, returning the original abstention and tracing
`appeal: errored`. Counted as `appealed` deliberately: if an errored appeal
reported nothing, a run where every retry crashed would show `appeals = 0` and
read as "the plan always declines" — the ambiguity the two counters exist to
separate.

### Three tests were theatre, and they were mine

`test_a_lost_appeal_reports_the_original_abstention` and two others built a
`Result` by hand and asserted on fields they had just set. **All three would
have passed with the entire appeal feature deleted.** No test drove the branch.

Replaced with six that stub `check_gates` and `llm.complete_json` — still pure,
but `answer_question`'s appeal branch actually executes: the error path, a won
appeal, a lost appeal returning the *first* call's reason rather than the
retry's more damning `fabricated_citation`, gate 5 still discarding a fabricated
citation on retry, the off switch making one call not two, and an answered
question never reaching the appeal at all.

### The defect found before the critic ran

For a non-windowed question the retry was **byte-identical** to the first call.
`llm._cache_key` hashes the messages, `FIRST_WIDTH == extract.MAX_SPAN`, and
`extract` truncates every snippet at that cap — so the truncation branch could
never fire. The cache would return the same refusal, count the tokens again, and
record `appealed=True, appeal_won=False`, which reads as "we looked again and it
is not there" when nothing was looked at. `plan_appeal` now declines with
`nothing new to show` unless there is a window to drop or a snippet longer than
the first render.

### Inherited by issue 23

**Today the appeal can only fire on a windowed question.** The width tier is
inert until `extract.MAX_SPAN` rises above `FIRST_WIDTH`, and that is pinned by
`test_today_the_appeal_can_only_fire_on_a_windowed_question` so nobody credits
the appeal with a recovery it cannot yet have made. Issue 23 owns raising the
cap and the on/off ablation.

Also inherited: no `Case` in `tests/test_fixtures.py` exercises the appeal, so
the zero-round-trip property is asserted by construction rather than measured on
a live graph.
